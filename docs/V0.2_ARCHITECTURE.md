# v0.2 implementation plan — OAuth, Home Assistant Cloud, native media player

Status: implementation plan; no production authentication changes shipped yet.

## Baseline
v0.1.0 uses a user-entered long-lived access token, event-bus subscription to `ha_android_media_player_command`, and `fire_event` for `ha_android_media_player_state`. Admin permission was required for the test event subscription. Do not use administrator credentials as the production workaround.

## Architecture
1. Android signs in against the user's Home Assistant instance with the Home Assistant authorization-code flow, PKCE S256, and an external browser. The client identifier must be a publicly reachable HTTPS page declaring the app's redirect URI per Home Assistant's mobile-app authentication requirements. Register an Android app link or a unique verified callback; validate redirect scheme, host, state, and PKCE verifier. Never embed a client secret in the APK.
2. Use the resulting short-lived bearer access token for `/api/websocket`; refresh it through Home Assistant's token endpoint and reconnect on expiry or invalid authentication. Store refresh credentials with Android Keystore-backed encryption; avoid logging tokens, authorization codes, and signed media URLs. Provide sign-out and token revocation.
3. Accept an HTTPS Home Assistant URL (including `*.ui.nabu.casa`). Connect with `wss://` and normal certificate validation; do not disable TLS verification. Do not assume that the cloud URL provides public access to private LAN media URLs.
4. Home Assistant custom integration exposes native `media_player` entities and dedicated WebSocket commands for device registration, heartbeat/state updates, and command delivery. Authenticate each command with the Home Assistant WebSocket connection's user context and enforce authorization at the integration boundary. Do not rely on unrestricted event-bus subscriptions or public `fire_event` access. Design device ownership and per-device permissions explicitly.
5. Commands: play_media, play, pause, stop, seek, set_volume; states: idle, buffering, playing, paused, error, unavailable. Device ID must remain stable across updates. The HA integration maps Media3 state and tracks heartbeats, reconnection, and availability.
6. For TTS and `media-source://` playback, resolve media inside Home Assistant to a device-reachable HTTPS URL, using short-lived authenticated/signed media access where supported. Verify external reachability through Nabu Casa; never expose permanent bearer tokens in media URLs.
7. Reconnection: exponential backoff with jitter, network changes, token refresh, resubscription/registration, and heartbeat timeout. The UI should report 'Authenticated', 'Registered', and 'Connected' separately, not report success before WebSocket registration is acknowledged.
8. Disable cleartext traffic in production once HTTPS-only onboarding is complete. Any LAN HTTP developer override must be opt-in, debug-only, and visibly labeled insecure.

## Delivery phases
- Phase A: Android OAuth/PKCE login, callback, encrypted token storage, refresh, HTTPS/WSS, and explicit connection status.
- Phase B: HA custom integration with config flow, device registry, media_player entities, custom authenticated WebSocket API, command/state mapping.
- Phase C: TTS and media-source resolution over cloud, lifecycle/reconnect tests, HACS metadata, docs, and CI.

## Acceptance tests
- Non-admin HA user can sign in and operate only authorized player entities.
- No long-lived token is manually entered or stored in plaintext.
- OAuth state mismatch and invalid redirect are rejected; expired access token refreshes without user intervention.
- Works via Nabu Casa HTTPS/WSS with certificate validation enabled.
- `media_player.play_media`, play/pause/stop/seek/volume, and `tts.speak` work end to end.
- App restart, HA restart, network switch, and token revocation have predictable outcomes.
- No sensitive tokens or signed URLs appear in logs.
